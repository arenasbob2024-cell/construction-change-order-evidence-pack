About

A smaller way to keep a change order together.

A free, browser-local tool for turning one change order and its photos into a printable record with a checksum you can re-check later.

Why it exists

On a small job, a change order rarely lives in one place. The scope change is in a text message, the approval is in an email, the measurements are on a paper note, and the proof is in a phone album. By the time someone asks “what did we agree to?”, the office is reconstructing the story from four apps.

Dedicated field platforms solve this well, but they are built around per-user subscriptions and a full project workflow. This page takes a narrower job: one change order, one PDF, one checksum. No account, no upload, no new system to administer.

What the tool does

  • Collects the project, change order number, date, contractor, client, work description, reason, amount change, schedule impact and notes.
  • Accepts up to 12 photos, each with a caption, resized and re-encoded in the browser so EXIF/GPS metadata is not carried into the PDF.
  • Draws a US-Letter PDF with a blank handwritten signature block.
  • Computes the PDF’s SHA-256 and writes a plain-text manifest with the filename, byte size and hash.
  • Lets you select a later copy of the PDF and compare its hash locally.

What it deliberately does not do

  • It does not upload or store your project file.
  • It does not create, apply or verify electronic signatures or identity.
  • It does not provide a trusted timestamp, notarization or legal certification.
  • It does not decide whether a change is authorized, whether an amount is correct, or whether a document will be accepted in a dispute.
  • It does not replace a contract, accounting system, project management platform or professional advice.

How the checksum is meant to be read

SHA-256 is a one-way digest of a file’s bytes. If the later file is byte-identical, the hash matches; if a single byte changes, it does not. That is useful for spotting a re-saved, edited or damaged copy. It does not establish when the file was created, who created it, or whether the events described in it happened. The PDF records the device’s local generation time for context only; it is not an external timestamp.

For a plain-language reference on how electronic records and authentication are treated in US federal evidence rules, see FRE 902. That reference is provided for orientation, not as legal advice. Authentication is only one of several separate questions a dispute can raise.

Technical transparency

  • The PDF is written by a small in-page writer using the PDF base-14 Helvetica fonts. It has no third-party JavaScript dependency.
  • Photos are decoded, drawn to a canvas, capped at a 1600 px long edge and encoded as JPEG at quality 0.85. This removes EXIF metadata and changes the image bytes.
  • Hashes use the browser’s Web Crypto API. No hash or file is sent to a server.
  • The site has no backend, database, account system, email capture, payment flow or third-party script.
  • The page is static and served from a free vercel.app address.
